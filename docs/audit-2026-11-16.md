# Codebase Audit — 2026-11-16

Full-project hardening pass: bug hunt, jank anatomy, and verification of every
item left open by the 2026-10-30 and 2026-10-16 audits. Method: baseline
test/lint run, four parallel deep reviews (hook/adapter write pipeline;
TUI read side and subprocess discipline; shell scripts, wiring, and
prior-fix verification; state/UI hot paths and selection logic), then manual
re-reading of every claimed anchor against the current bytes before it was
recorded here. No live reproductions were needed — every confirmed finding is
visible in the code paths themselves.

Motivating report from the user: occasional jank, and one long-lived OpenCode
session in which **two OpenCode agents "wigged out" and one was writing to the
other's title**. The second item is explained exactly by finding #1.

## Confirmed bugs

### 1. `.opencode/plugins/tmux-agent-sidebar.js:210-218` — ≥8-char title-prefix match misroutes events and re-points the other pane's binding *(the reported symptom)*

`titlesMatch` accepts any pane title that is a ≥8-character prefix of the
session title:

```js
if (pane === session) return true;
return pane.length >= 8 && session.startsWith(pane);
```

Auto-titled OpenCode sessions routinely share long prefixes ("Refactor the
auth flow" / "Refactor the auth flow in the API"). With two sessions in the
same directory:

1. Session B's event resolves (`resolvePaneId`, js:293-316): `titled`
   matches **pane A** (A's stamped title is a ≥8-char prefix of B's title),
   and the `titled && (!bound || bound.id === titled.id)` branch chooses
   pane A with `committed = true`.
2. The spawned hook's `sync_pane_location` (`src/cli/hook/context/location.rs:108-125`)
   sees `@pane_session_id` (A's) ≠ sid (B's), **unsets `@pane_session_title`,
   and rewrites the binding to B** — a permanent re-point, not a transient.
3. B's next `session.renamed` event passes the tracked-session check
   (`src/cli/hook/handlers/session.rs:79-82`) and stamps B's title onto
   pane A's row.

A's own events then fight back through the same branch, producing the
symmetric "wigging" — both rows animating with the other session's state,
titles flapping, until the session titles diverge past the prefix. The
`committed` doctrine (js:278-283) exists precisely to prevent recording
guesses, but a prefix-match hit is treated as committed title evidence.

**Fix:** require near-exact agreement (equal, or pane title equal to the
session title truncated to the pane-title length), and demand binding
agreement before the `titled`-versus-`bound` conflict branch may commit a
binding rewrite.

### 2. `.opencode/plugins/tmux-agent-sidebar.js:358-365` — daemon `TMUX_PANE` fallback is committed and unguarded

When nothing matches by path or binding, `resolvePaneId` falls back to the
daemon's own `process.env.TMUX_PANE` (the pane that booted
`opencode serve --service`, possibly a shell, possibly long gone) after only
an existence check — and `committed` stays at its `true` default (js:285),
so the hook writes full run state *and the session binding* into that
unrelated pane. This is the permanent-misroute case the
`TMUX_AGENT_SIDEBAR_BIND_SESSION=0` flag was built to defuse
(`location.rs:84-89`); this path never sets the flag.

**Fix:** set `committed = false` on this fallback, and require the pane to be
one of the `opencode`-command candidates.

### 3. `.opencode/plugins/tmux-agent-sidebar.js:170,227,325` — free-claim + 2 s pane cache can double-claim one pane

Two brand-new same-directory sessions both take the `free` claim
(`pathMatches.find(p => p.sessionId === "")`, js:325) for the *first*
unbound pane. Resolution chains are serialized, so normally A's binding
lands first — but the `PANE_CACHE_MS = 2000` cache (js:170,227) can hand
session B a resolution captured before A's binding write, and every event
routed through the stale cache entry commits the binding flip (clearing the
other pane's title, per #1). Same symptom class, shorter window.

### 4. `src/cli/hook/handlers/run.rs:152-159` — `on_stop` unsets `@pane_subagents` outside the subagent lock

Both subagent hook paths take the per-pane flock (`subagent.rs:69,84`), but
Claude's `Stop` cleanup reads and unsets the list with no lock, to clear
stale children after a synchronous turn. Interleaving with a concurrent
`SubagentStop` (which read the list *before* the unset): the stop rewrites
a stale value resurrecting the removed children. Consequence chain:
`pane_writes_allowed` (`location.rs:119-122`) stays false, freezing the
parent's metadata writes, and the parent's later `SessionEnd` bails at the
subagent guard (`session.rs:110-112`) — stale row state until the next
parent `Stop` re-clears. Recoverable, but it is the exact lost-update class
the flock was added for. **Fix:** move the read+unset inside
`with_subagent_lock`.

### 5. Hook hot path: every identity-bearing event pays ~18–25 tmux spawns + a git probe

Traced end-to-end from `cmd_hook` (`src/cli/hook.rs:15-77`):

- `sync_pane_location` (`meta.rs:43` — run on SessionStart, UserPromptSubmit,
  Notification, Stop, StopFailure, PermissionDenied, …) calls
  `with_live_worktree` (`location.rs:141-160`), which — whenever the payload
  carries no worktree name/branch, i.e. every Codex/OpenCode/Hermes/agy
  event and every non-worktree Claude event — spawns
  `tmux display-message "#{pane_current_path}"` **plus a 6-arg
  `git rev-parse`** (`location.rs:165-182`, 5 s timeout) plus two
  conditional unsets. A steady `UserPromptSubmit` lands ≈ 18–20 tmux
  spawns + 1 git; a `Stop` ≈ 24–28 + 1–2 git.
- Every notification-gated event first calls `notification_settings()`
  (`hook.rs:124,156,175,193,234,256` → `DesktopNotificationSettings::from_tmux`),
  which does a full `tmux show -g` **and** unconditionally spawns
  `notify-send --version` / `osascript -e "return 0"`
  (`desktop_notification.rs:83-84,272-295`) — the probe runs even when
  `@sidebar_notifications off`.
- Every state-changing event ends with `notify_sidebars_of_pane`
  (`hook.rs:75-78` → `notify_focus.rs:7-27`): `display-message` +
  `list-panes` + an identity check per pid.

Nothing is batched — every option access is its own tmux process
(`src/tmux/options.rs:441-472`). On a loaded box each spawn is 5–20 ms, so a
Stop event's own latency budget is hundreds of ms; the agent-side hook
timeout budgets get eaten, and (for OpenCode) the serialized bridge
`hookChain` (js:106,376, 3 s cap) means **a wedged hook for session A
delays every other session's events in the same daemon**. This is the
second jank channel: the TUI itself is not blocked by it, but the state
transitions arrive late and bunched.

**Fix ideas:** cache the worktree probe per pane path (the answer cannot
change while the pane's cwd is unchanged); probe the notification backend
only after the enabled check short-circuits (move the probe behind
`read_bool(...).unwrap_or(true)`); batch option writes into one
`tmux set` argv (one process can set many `-p -t` pairs… at least per key,
and `show -g` results are already fetched in one call elsewhere).

### 6. `src/cli/hook/activity.rs:142-143,166-167` — `agy` CLI alias silently disables the antigravity activity guards

`resolve_adapter` accepts the `agy` alias (`src/event/adapter.rs:22`), but
`handle_activity_log` compares the **raw CLI argument** against the
canonical `ANTIGRAVITY_AGENT` label. A hooks.json wired as
`hook agy activity-log` loses the pending-action wait-stickiness guard and
the `__`-pseudo-tool churn suppression: idle panes glow after
`__task_reset__` churn, prompts get stomped. The run-state handlers are
immune because they use the adapter-supplied canonical name — the
asymmetry is the bug. Generated snippets use the canonical label, so
reachability is limited to hand-wired configs, but the fix is one
normalization at dispatch.

## Anatomy of the jank

Ranked by measured-by-reading cost on the render thread. The tmux *spawn*
for `list-panes` was correctly moved to a worker (`app/workers.rs:151-172`);
what was left behind is not pure string work.

### J1. `ps` runs on the render thread on every snapshot apply — primary suspect

`app.rs:179-183` → `apply_session_refresh` (`state/refresh.rs:507-513`) →
`build_session_snapshot` (`tmux/query.rs:192-198`) → `process_snapshot_for_panes`
(`query.rs:823-830`) → `ProcessSnapshot::scan()` (`process.rs:26-36`,
`PS_TIMEOUT` 5 s; its own comment at `process.rs:9-10` admits "it runs on
the TUI event loop every refresh tick"). The worker comment at
`app/workers.rs:46-50` ("the parse is string work, safe to run where
`AppState` lives") is **false**: the parse includes a full-system `ps -ww -eo`
plus tree walks.

- The scan is armed whenever any pane is a non-agent pane
  (`pane_output_has_other_panes`, `query.rs:832-846`) — i.e., in practice,
  always, since every workflow has shell panes.
- Signal-driven refreshes coalesce at `MIN_REFRESH_GAP = 150 ms`
  (`app.rs:26,111`), and every hook event pokes the sidebar
  (`hook.rs:75-78`). During a busy agent's tool stream the render thread
  therefore runs a full `ps` scan roughly **6–7×/s**, each blocking input
  for its duration (10–40 ms healthy; the `subprocess.rs` timeout+drain
  path stretches pathological cases toward ~12 s of frozen UI).
- `sweep_dead_bg_shells` (`refresh.rs:887-899`) can pay a *second* inline
  `scan()` every 5 s when the build-path snapshot was `None` and any pane
  holds a background shell.

**Fix:** move `ProcessSnapshot::scan()` into the snapshot worker next to
`list-panes` and ship both halves over the channel. This one change removes
the dominant per-tick blocking call.

### J2. Enter/jump pays ~12–20 serial tmux spawns inline

`activate_selected_pane` (`state/focus.rs:193-278`): `select_pane` (~5
spawns) → `display_message` for `window_id` / `window_width` /
`popup_max_width` / `pane_current_path` (4 more) → `cmd_toggle --create-only`
(~6–12). All synchronous on the input thread, each bounded at 3 s
(`subprocess.rs`). Pathological worst case ≈ a minute of dead UI; healthy
case 30–80 ms, but it *feels like* Enter lag exactly when the server is
busy — which is exactly when you press Enter to switch agents.

### J3. Shared-option toggles broadcast through an untimed fallback

`broadcast_change` (`state/global.rs:211-213`) → `broadcast_refresh`
(`tmux/signal.rs:59+`): `list-panes -a` plus `is_sidebar_process` per pid;
the fallback branch (`signal.rs:33-38`) spawns `ps -p … -o comm=` with bare
`.output()` — **no timeout wrapper at all**. On Linux it is normally the
`/proc/<pid>/exe` readlink, but for dead/recycled pids (and always on
macOS) that is one untimed `ps` per anchor pid, per toggle, on the UI
thread.

### J4. `clear_agent_pane_state`: 19 inline tmux unsets *during parse*

`query.rs:689-719`: when a Codex/OpenCode/Hermes/agy pane is confirmed dead,
teardown fires 19 sequential `unset_pane_option` spawns plus a file removal,
from inside `parse_pane_fields` on the render thread. Healthy ≈ 19 × 3 ms
per teardown; wedged-tmux ≈ 57 s theoretical ceiling. (The teardown
decision itself is now correctly guarded — see "Verified clean".)

### J5. Smaller per-keystroke offenders

- `x` remove-confirm runs `git status --porcelain` + `git rev-list` inline
  as warnings pre-flight (`state/popup.rs:656-673`, `worktree/flow.rs:154-165`,
  5 s timeouts) — the *removal* moved to a worker (`popup.rs:681-702`), the
  pre-flight did not.
- `y` clipboard copy: `set-buffer -w` falling back to `set-buffer`
  (`clipboard.rs:32-41`) — two serial 3 s-timeout spawns on some paths.
- `r` resume with a `@ path` hint launches inline (`state/todo.rs:730,747`,
  ~6 spawns); the no-hint path correctly uses the popup-op worker.
- `s` regroup deliberately runs `refresh()` — `list-panes` **and** `ps` —
  on the UI thread (`refresh.rs:470-498`); documented as intentional, but
  it is the worst single-keystroke stall in the app.

### J6. Steady-state churn that is never free

- Globals/window-inactive folds call `rebuild_row_targets`
  (`app.rs:270-299`); the rebuild builds `filtered_panes` +
  `matched_windows` vectors per group (`layout.rs:171-206`) and the
  renderer's `collect` builds the same vectors again per frame
  (`ui/panes/row_collector.rs:67-109`). Same work, twice, every frame the
  list is rebuilt.
- Idle panes re-read and re-parse their whole activity log every tick even
  when the mtime is unchanged: the skip is `log_unchanged && agent_active`
  (`refresh.rs:749-758`), so *inactive* panes always re-read "for the
  grace path" — file I/O × N idle agents × 1/s. Capped at ~210 lines, but
  free to fix by re-reading only when the grace timer is actually running.
- Chyron banner string built twice per frame while scrolling
  (`chyron.rs:222-264`, `is_showing` → `banner()` then render again);
  todo items wrapped twice per frame (`ui/panes/todo.rs:103-104` vs
  `:236-237`) and `park::recognize_resume` (two regexes) re-run per item
  per frame (`ui/panes/todo.rs:228`).
- `jump_to_next_attention` (`layout.rs:349`) runs the window-attention scan
  per candidate row — O(rows × windows) per keypress.

## Likely bugs (traced in code, timing- or platform-dependent)

Status (2026-11-17, post 1.3.1): eight of the nine were real and are fixed
(batches 5–8 below); one was a phantom. Per-item verdicts appended to each
bullet.

- **`state/layout.rs:253-261` — selection drift on row removal while
  unfocused.** Outside search, when the cursor's pane disappears the
  cursor clamps to `len - 1`; on return, keep-in-view scrolls *down* to it.
  This is the exact surprise commit 7cbe4e5 set out to kill, surviving the
  row-removal path (the pane-id re-anchor only runs when the pane
  survives). Fix: re-anchor by *position in the group* rather than
  clamping the index.
  → FIXED: `rebuild_row_targets` captures (group, offset-within-group)
  before the rebuild and re-anchors the cursor inside the surviving group;
  the global clamp remains only when the whole group is gone. Pinned by
  `test_rebuild_row_targets_reanchors_within_the_group_on_removal` and
  `..._clamps_when_the_whole_group_goes`.
- **`state/panes.rs` (`apply_auto_scroll`) — preserved cursor in the lower
  half jumps the viewport** on refocus (offset preserved only when cursor
  < half). Suspected; matches "viewport jumps when I tab back".
  → FIXED (anchor corrected: the real path is `reset_pane_scroll` +
  `compute_scroll_offset`, `ui/panes.rs:589`). The unfocus tick parked the
  scroll offset at the top while preserving the cursor, so the focus-gated
  auto-scroll dragged the viewport down to the cursor on refocus whenever
  the context pane was unknown or filtered out. The offset is no longer
  parked: the viewport (and cursor) survive the trip exactly as left, and
  only the intentional context reconciliation still scrolls. Pinned by
  `test_window_switch_preserves_cursor_and_viewport` and the
  `select_focused_context_row` tests in `state/scroll.rs`.
- **`.opencode/plugins/tmux-agent-sidebar.js:473,550-552` — default-allow
  window after daemon restart.** Everything passes `belongsToInstance`
  until the first owned `session.created`; a foreign-project event can
  claim a pane on the daemon's first event. Mitigated by the one-time
  attribution probe, not eliminated.
  → FIXED (narrower than described: `knownSessionBelongs` already consults
  the probe for unknown sessions, so the real hole was a *thrown* probe).
  A thrown `session.get` (transient RPC failure) used to be cached as a
  permanent miss, default-allowing that session for its whole life. Misses
  the server actually answered are still cached; throws now retry on the
  next event. Pinned by "a transient lookup failure is retried, not cached
  as a miss" in the bridge test suite.
- **`src/cli/hook/handlers/session.rs:79-87` — session-title get-check-set
  is unguarded** and ignores `TMUX_AGENT_SIDEBAR_BIND_SESSION`; two events
  racing onto an unbound pane both pass the `tracked == ""` check, last
  write wins. The CLI-side complement of findings #1/#3.
  → FIXED: an unbound pane no longer adopts a title from a bridge-guessed
  route (`TMUX_AGENT_SIDEBAR_BIND_SESSION=0` gates the title like the
  binding), and the title check+write holds the same per-pane flock as the
  binding read-modify-write in `sync_pane_location`, so the two identity
  writers cannot interleave. Pinned by
  `on_session_title_guessed_route_does_not_claim_an_unbound_pane` and
  `on_session_title_waits_for_the_identity_lock`.
- **`src/desktop_notification.rs:176-187` — notification-stamp RMW is
  unguarded**: concurrent identical events can double-notify.
  → FIXED: the check → send → stamp-write sequence holds the pane's
  per-pane lock (new shared helper `paths::with_pane_lock`, pinned by the
  thread test in `paths.rs`).
- **`src/cli/hook/activity.rs:114-125` — `@pane_bg_pid` overwrite-or-clear**
  ordering is not protected; two concurrent background spawns can leave the
  placeholder clearing the other's pid.
  → FIXED: the `@pane_bg_cmd` + `@pane_bg_pid` pair write holds the pane's
  per-pane lock. Pinned by `handle_activity_log_bg_pair_waits_for_the_bgcmd_lock`.
- **`src/adapter/antigravity.rs:161` — transcript tail opens the payload
  path with bare `File::open` and no tilde expansion**, while a captured
  real payload fixture carries a literal `"~/.gemini/…"` path. If agy emits
  `~`-relative paths, prompt/response recovery silently returns `""`
  forever. Needs one real payload to confirm.
  → FIXED: `transcript_tail` expands a leading `~/` against `$HOME`
  (confirmation not needed — the repo's own captured-payload fixture in
  `adapter/antigravity.rs` tests carries the literal `~/.gemini/…` path).
  Pinned by `expand_tilde_resolves_a_leading_home_tilde`.
- **`src/park.rs:359-362 — cwd probe aborts on the first unreadable
  transcript.** `File::open(&transcript).ok()?` inside the projects walk
  loop returns `None` outward instead of `continue`; with nondeterministic
  walk order the resume cwd hint becomes flaky. (Confirmed by reading;
  impact is cosmetic-to-annoying.)
  → FIXED: unreadable transcripts `continue` the walk. Pinned by
  `projects_probe_skips_an_unreadable_transcript`.
- **`src/park.rs:473-482` — `window_launch_ok` accepts a stale same-named
  window older than 5 s**, so a leftover window can fake "launched ok";
  `:496` `trim_matches('\'')` strips *all* edge quotes from a tmux-doubled
  compare, mis-comparing cwds with edge quote chars.
  → PHANTOM: no `window_launch_ok` (or any `trim_matches`) exists in
  `src/park.rs` at the audit's commit (7cbe4e5) or HEAD; the park.rs
  region at those lines is the `ResumeEnv` trait. Dropped without a fix —
  if the underlying concern is real, it lives somewhere else and needs a
  correct anchor.

## Wiring and deploy findings

- **`.github/workflows/ci.yml` never runs the OpenCode bridge test suite.**
  `.opencode/plugins/tmux-agent-sidebar.test.mjs` exists and is well-built,
  but CI is `cargo test`/`clippy`/`fmt` only, and no cargo test binds the
  bridge's event surface to the Rust parse arms (OpenCode has no
  `HOOK_REGISTRATIONS` table — it is wired entirely through the bridge).
  This is the one wiring layer that can drift silently today. Fix: a cargo
  test that shells to `node --test` when node is present, or a table test
  comparing the bridge's event strings against the parse arms.
- **`install-wizard.sh:20` sources a hardcoded `~/.tmux.conf`.** XDG-only
  setups (`$XDG_CONFIG_HOME/tmux/tmux.conf`) never reload after install.
- **`install-wizard.sh:170-171`: wizard menu actions break on spaces** —
  `new-window "$PLUGIN_DIR/install-wizard.sh download-binary"` is
  re-parsed by tmux and splits on a spaced plugin path (the entry script's
  own invocations are correctly quoted).
- **`tmux-agent-sidebar.tmux:18-24`: version-check wizard loop.** A
  checkout whose `Cargo.toml` is ahead of the last published tag (post
  `make bump`, pre-tag) trips the install wizard on *every* conf load, and
  the wizard's own `tmux source` re-triggers it. Documented as the
  "version-check gotcha" in AGENTS.md, not mitigated in code — a
  dev-checkout escape hatch env var would end it.
- **`fixtures/scenarios/common/_lib.sh:113`: cleanup's activity-log `rm` has
  no TMUX_TMPDIR sentinel guard** (the `kill-server` above it does). Run
  without `setup()` on a host with no `XDG_RUNTIME_DIR`, `activity_dir()`
  resolves to `/tmp` — the same fallback `paths.rs` uses — and the glob
  deletes the *live* sidebar's logs.
- **README.md:93-97 development tip is a trap:** symlinking the checkout
  over the plugin dir keeps whichever stale `bin/` binary the wizard once
  downloaded (the entry script prefers `bin/` over `target/release/`).
  AGENTS.md's copy-the-artifact procedure is correct; align the README.
- **Conf-load hook dedup (`agent-sidebar.conf:153-164`) — one unverifiable
  link:** the dedup pipes `show-hooks` output including its `[N]` index
  suffix into `set-hook -gu '<hook>[N]'`. If the server rejects indexed
  names, every reload *adds* a duplicate (failures are swallowed by
  `xargs`). A 30-second scoped-server probe (register twice, run the line,
  count entries) should settle it; the live server's known-clean state
  suggests indexed names are accepted, but nothing pins it.
  → VERIFIED WORKING (2026-11-17, scoped `tmux -L dedup-probe` server,
  tmux 3.8): the exact dedup line removes both of two `-ga`-registered
  duplicate entries, and four simulated reload cycles (dedup → `-ga`
  re-register) hold steady at exactly one entry. Indexed
  `set-hook -gu 'name[N]'` is accepted; no duplicate accumulation.
  Closed without a fix.
- **`src/cli/setup/mod.rs:139`: `build_antigravity_snippet` silently
  overwrites** two registrations sharing a trigger (the JSON-map insert
  has no push semantics, unlike `build_agent_snippet`). Harmless today.

## Verified clean (checked, not assumed)

- Parse-time teardown no longer wipes on unknown: missing snapshot or
  unparsable pid is "unknown, don't wipe" (`query.rs:563-572`); repeated-dead
  needs `REQUIRED_DEAD_SCANS = 2` consecutive confirmed misses with
  reset-on-hit (`refresh.rs:855-885`); a failed scan never advances streaks.
- Injection: all tmux/git calls are argv vectors; `park.rs` validates
